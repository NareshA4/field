# Decision log

Format: ID, decision, why, consequence. All are FieldOps implementation decisions unless marked HPE.

- **D-001 Django 5.2 LTS.** HPE requires 4.2+; 5.2 is the current LTS. Python 3.12 in Docker, 3.11+ supported.
- **D-002 Functional app names; M-numbers are traceability only** (`docs/TRACEABILITY.md`).
- **D-003 UUID primary keys** everywhere: no enumerable IDs in URLs/APIs (also helps M12 QR requirement).
- **D-004 Tenant model.** Every tenant record carries `organization` FK (PROTECT). Default manager `TenantManager` filters by the active org and is FAIL-CLOSED in the request cycle (starts as "no tenant" -> empty). Escape hatch `.unscoped()` is allow-listed by a test. Cross-tenant writes are rejected in `save()`. Postgres RLS is optional later hardening (not required now).
- **D-005 Roles are per-organization rows** seeded from additive templates (`rbac/role_templates.py`, fnmatch patterns over the registered permission catalog). Orgs may edit defaults and create custom roles. Owner role = implicit all permissions, locked, not editable. Seeded defaults are defaults, not restrictions.
- **D-006 Invitation of existing users.** An existing account invited to another org is activated immediately and notified (no acceptance step). Revisit if consent is required.
- **D-007 No plaintext passwords.** Owners/users activate via signed, expiring (3 days), single-use token links and choose their own password (>= 12 chars, Django validators). Platform admin created by CLI reading `FIELDOPS_ADMIN_PASSWORD`/prompt, never argv.
- **D-008 Platform admin has no tenant rights.** `is_platform_admin` is independent of org roles; Owner never inherits it; platform console runs in explicit PLATFORM tenant mode.
- **D-009 Active-org selection.** Session (UI) or `X-Organization` header (API) only SELECTS among the caller's own ACTIVE memberships; nothing is granted by the value (tested).
- **D-010 API auth:** JWT (simplejwt, 15 min access / rotating refresh) + session; login throttled; axes lockout (5 failures / 15 min).
- **D-011 Error envelope** `{"error":{code,message,details,request_id}}` for all API errors.
- **D-012 Audit immutability in 3 layers:** model/queryset guards + PostgreSQL trigger blocking UPDATE/DELETE. TRUNCATE is not trapped (would break test flush); organizations are never hard-deleted (PROTECT).
- **D-013 Workflow engine** `core.workflow.StateMachine`; services own transitions + audit in one transaction.
- **D-014 UI:** Django templates + HTMX + Bootstrap 5 (vendored, pinned; no runtime CDN). No React until a widget justifies it.
- **D-015 Static files** via WhiteNoise inside the app image (Nginx proxies); media on a volume; S3-compatible storage later if needed.
- **D-016 Environments.** Local/test: Docker Postgres (never Supabase). Production DB: Supabase Postgres project `fieldops-nexus-prod-sg` (ap-southeast-1) via Django `DATABASE_URL` (Django migrations, not Supabase migrations). Redis: Render Key Value (Singapore) when available.
- **D-017 Site-scoped permissions** deferred to Phase 1 because they need `sites.Site`.
- **D-019 Supabase isolation.** Production tables live in schema `fieldops` owned by least-privilege role `fieldops_app` (created by `scripts/provision_supabase.py`). `anon`/`authenticated`/`service_role` have no USAGE on it, so Supabase's REST Data API cannot reach tenant data; Django remains the only gateway. The Supabase "RLS disabled" advisory is therefore not exploitable for these tables; RLS may still be added as defence in depth. The admin (`postgres`) credential is used only for provisioning.
- **D-020 Third-party static files** live in `src/static/lib/` (renamed from `vendor/`, which some tools skip), fetched by `scripts/fetch_static_libs.py` with source-map comments stripped.
- **D-021 Local HTTP stack toggles:** `DJANGO_SECURE_COOKIES`/`DJANGO_SECURE_SSL_REDIRECT` default to secure; compose sets them false for http://localhost:8080 only. Nginx forwards `Host` with port (`$http_host`) so Django's CSRF origin check works.
- **D-022 Git/CI.** Local repo initialised with `main`; baseline commit = verified Phase 0 (needed so per-phase sessions can use git worktrees). GitHub remote pending (connector failed). Branch model per `DEVELOPMENT_RULES.md`: each phase on `feature/phase-N-*`, merged to `main` after Team Lead approval.
- **D-023 Login throttling model (incident 2026-10-03).** Axes locks on the *combination* username+IP (not either), using the credential key Django actually passes (`username`), normalised (strip/lower). Client IP comes from `apps/core/net.client_ip`, which trusts `X-Forwarded-For` only for `TRUSTED_PROXY_COUNT` hops from the right (0 = never). Same function feeds the audit log. Lockout shows a friendly 429 page. Nginx rate-limits only credential POSTs. Super Admin stays `is_platform_admin` without `is_staff`/`is_superuser`. Details: `docs/INCIDENT_2026-10-03_LOGIN.md`.
- **D-024 Operator-facing secrets handling.** Passwords are never passed on a command line or typed inside double-quoted PowerShell strings; use the hidden prompt (`create_platform_admin`, `changepassword`, `diagnose_login`) or single-quoted values.
- **D-018 Celery:** `acks_late`, JSON, time limit; beat runs `clearsessions` daily; module phases add PM/SLA/expiry tasks. Tasks touching tenant data must use `tenant_context(org)`.
- **D-025 Site-scoped roles (Phase 1).** `rbac.MembershipRole.site` (nullable FK): NULL = organization-wide, else the role applies to that site only. Only permissions registered with `site_scoped=True` are honoured per site (site/zone/calendar/asset families); `user.*`, `role.*`, `organization.*`, `site.create`, `asset.category.manage` stay organization-wide, so a site assignment can never widen org-level rights. Owner is always org-wide. `has_permission(m, code, site=None)` is strict (org-wide unless a site is given); `has_permission_anywhere` is the endpoint gate; `site_scope()` restricts every list/detail query. Out-of-tenant or out-of-scope ids answer 404, visible-but-not-permitted answers 403.
- **D-026 Asset hierarchy (M03) = `AssetComponent` edges.** Single store of structure (no duplicate `Asset.parent`): `child` is OneToOne (one parent, a forest), relationship ASSEMBLY / COMPONENT / REPLACEABLE_PART, quantity, part_number (bridge to M09). Rules: same organization AND same site, no self/cycle, depth <= 8, RETIRED/DISPOSED assets cannot join/leave, per-organization advisory lock serialises concurrent edits, moving an asset's site is refused while it is in a hierarchy.
- **D-027 Asset status transitions (needs Team Lead approval).** HPE chain implemented as: ACTIVE -start_maintenance-> UNDER_MAINTENANCE; UNDER_MAINTENANCE -complete_maintenance-> ACTIVE or -mark_out_of_service-> OUT_OF_SERVICE; OUT_OF_SERVICE -return_to_service-> ACTIVE, -retire-> RETIRED, -dispose-> DISPOSED; RETIRED/DISPOSED terminal. `complete_maintenance` is an addition needed to leave maintenance; direct ACTIVE -> OUT_OF_SERVICE is deliberately NOT allowed (not in the HPE chain). Status changes only through `assets.services.change_status` (reason required, append-only history, audit).
- **D-028 Attachment authorisation registry.** `files.access.register("<app>.<model>", checker)` lets a module authorise downloads per target (asset documents follow the asset's site scope). Targets without a checker keep the Phase 0 `read_permission` rule.
- **D-029 Deletion policy.** Sites, zones, assets and categories are never hard-deleted (PROTECT FKs); they are deactivated/retired. Deactivation is refused while active (non-terminal) assets exist. Calendars, holidays and contacts (pure configuration) may be deleted, with audit.

- **D-035 M05 Incident / Service Request design (OUR IMPLEMENTATION DECISIONS; HPE gives the state chain and scope only).** App `incidents`. `ServiceRequest` (kind INCIDENT | SERVICE_REQUEST, severity LOW..CRITICAL, service impact NONE/DEGRADED/PARTIAL_OUTAGE/FULL_OUTAGE + notes, asset FK, site = asset's site, reporter = Membership, `occurred_at`), `Downtime` (one per request; start required, end open until restored; ends automatically when the work order is completed, or manually with `incident.downtime.manage`), append-only `ServiceRequestHistory`, evidence through `files.Attachment`. Chain NEW -> TRIAGED -> APPROVED/REJECTED -> WORK_ORDER_CREATED -> IN_SERVICE -> RESOLVED -> CONFIRMED -> CLOSED. `link_work_order`, `work_order_cancelled`, `start_service`, `resolve`, `resume_service` are SYSTEM actions applied only by the M05/M06 hooks (`incidents.services.on_work_order_*`), never accepted from the transition API/UI. Additions beyond the HPE chain: `reopen` (RESOLVED -> APPROVED, reason required; a new work order can then be created) and the return path WORK_ORDER_CREATED -> APPROVED when the work order is cancelled. Approving does not create a work order automatically: a user with `work_order.create` presses "Create work order" (M05 creates a real M06 DRAFT work order through `workorders.services.create_work_order`). **CLARIFICATION REQUIRED (HPE/Team Lead):** the master workflow says the asset "may become UNDER MAINTENANCE per the approved rule" when a work order starts, but no rule is recorded; Phase 2 therefore does NOT change asset status automatically (no hidden coupling). Likewise "downtime may end" at work-order close: implemented as ending at work-order completion (service restored); change if the Team Lead prefers closure.
- **D-036 M06 Work Order design (OUR IMPLEMENTATION DECISIONS unless stated).** App `workorders`. HPE CONFIRMED chain DRAFT -> PLANNED -> ASSIGNED -> DISPATCHED -> IN_PROGRESS -> ON_HOLD (back to IN_PROGRESS) -> COMPLETED -> SUPERVISOR_REVIEW -> CLOSED, never DRAFT -> CLOSED. Added: `reject_review` (SUPERVISOR_REVIEW -> IN_PROGRESS, rework, reason) and `cancel` (only before work starts, reason) -> CANCELLED. Single assignee per work order (`assigned_to` Membership); re-assignment of ASSIGNED/DISPATCHED orders keeps the state. Invalid technician allocation is refused: other organization, inactive, lacks `work_order.start` for the site, or committed to another live work order with an overlapping planned window. Execution (start/hold/resume/complete) belongs to the assignee, with a dispatcher (`work_order.dispatch`) allowed to act for them. Capture: labor (hours per technician per day, 0 < h <= 24, not future), materials as free-text consumption lines (M09 owns stock; these lines move no stock), evidence via `files.Attachment`. Closure rules: resolution notes (>= 10 chars, set at completion), at least one labor entry, and for CORRECTIVE/INSTALLATION work at least one evidence file (checked at completion and at closure). **OPEN:** "closure requires checklist completion" (HPE) cannot be enforced until M08 exists (Phase 3): `workorders.services.closure_blockers` is the single place to add it. One live work order per request (DB partial unique index; cancelled/closed ones do not block rework).

- **D-039 M08 Inspection & Checklist Engine design (OUR IMPLEMENTATION DECISIONS; HPE gives scope only: templates, mandatory fields, exception findings).** App `checklists`. `ChecklistTemplate` is versioned: `key` groups versions, `version` increments, DRAFT -> ACTIVE -> INACTIVE; an ACTIVE/INACTIVE version is FROZEN (items cannot change; `new_version` copies it into a new DRAFT, activating it deactivates the previous active version of the same key), so a historical inspection always shows the questions it was answered against; DB: one ACTIVE version per key. `ChecklistItem` types TEXT / NUMERIC (min/max/unit) / BOOLEAN (pass/fail) / SELECTION (options + exception options), `required`, `guidance`, `evidence_required`, ordered by `position` (deferred unique). An answer is an EXCEPTION when a boolean is fail, a number is outside min/max, or a selection is an exception option; every exception needs a `Finding` before the inspection can be completed; items flagged `evidence_required` need a file (`files.Attachment` on the answer). `Inspection` = one execution (template version, work order or asset, site, started/completed by); IN_PROGRESS -> COMPLETED is terminal and immutable (DB check: completed has a timestamp); duplicate execution of the same checklist (any version of the key) on a work order is refused (service + partial unique index). Execution requires the work order to be IN_PROGRESS and the caller to be its assignee or a dispatcher (M06 rule via `workorders.services.assert_can_execute`) plus `inspection.execute` for the site. `Finding` keeps inspection, item, work order, asset, site, description, severity LOW..CRITICAL, status OPEN/RESOLVED, creator, timestamps, resolution. Permissions: `checklist.view|manage|execute` (organization-wide) and `inspection.view|execute|review` (site-scoped); technicians see an inspection only when they started it or the work order is assigned to them. Role templates (additive): operations_manager gains `checklist.*`, `inspection.*`; planner gains `checklist.manage`, `inspection.view` (supervisor/technician patterns already existed).
- **D-040 M08 -> M06 closure integration (OUR IMPLEMENTATION DECISION; resolves the OPEN item "closure requires checklist completion").** `checklists.services.checklist_blockers(wo)` reads persisted rows only and is called from the ONE existing M06 mechanism: `workorders.services.closure_blockers` (so the `close` guard and the `/closure/` API report it) and the `complete` guard (`code=checklist_incomplete`, 409). A template is "required" when ACTIVE, `is_required` and `work_type` is blank or equals the work order's type; the order needs a COMPLETED inspection of any version of that checklist; any unfinished inspection of a required checklist blocks too (deactivating a template mid-way cannot skip it). No required template = unchanged M06 behaviour. Applicability is evaluated live, so activating a new required template also applies to open work orders that have not been completed/closed yet (a deliberate, documented consequence; a snapshot-at-start model would need Team Lead confirmation).

- **D-042 M09 Spare Parts & Inventory design (OUR IMPLEMENTATION DECISIONS; HPE gives scope only: warehouse/site stock, issue/return, reservations, min-max, transfer, consumption against work orders; the Part Request chain is HPE CONFIRMED).** App `inventory`. Entities: `Warehouse` (one site, code unique per organization), `Part` (catalogue, organization-wide, part number unique case-insensitive, default min/max/reorder), `StockBalance` (warehouse x part: `on_hand`, `reserved`, `available = on_hand - reserved`, optional per-warehouse min/max/reorder override; DB checks on_hand >= 0, reserved >= 0, reserved <= on_hand), `StockMovement` (append-only ledger: RECEIPT, ISSUE, RETURN, TRANSFER_OUT/IN, ADJUSTMENT, RESERVE, RELEASE; signed on-hand and reserved deltas + resulting balance; DB check "a movement changes the balance"), `WorkOrderPart` (the part requirement of a work order: requested / issued / consumed / returned quantities, one line per (work order, part)), `PartReservation` (stock-side hold of a line; sum of ACTIVE holds == `StockBalance.reserved`, a tested invariant). Invariant: every quantity change goes through `inventory.services._apply`, which re-checks the rules, saves the balance and writes exactly one movement in the caller's transaction; lock order is work order -> part line -> reservation -> balance (two balances in primary-key order, destination existence ensured without locking: a real deadlock was found by the concurrency tests and fixed). Consumption changes no stock (stock left the warehouse at ISSUE): it is recorded on the line, audited and written to the M06 material list through `workorders.services.record_material`, so `WorkOrderMaterial.part_line` (new nullable FK, migration `workorders.0002`) marks stock-backed rows while existing free-text rows stay valid and keep meaning "non-stocked consumable, no stock moved". Part-line status is recomputed from the quantities in one place (`_refresh_status`; partial reserve/issue/consume/return make an action's target depend on quantities); RECONCILED and CANCELLED are real state-machine transitions. Rules: warehouse site must equal the work order's site; a line is committed to one warehouse while stock is reserved/issued; request/reserve/issue only while the work order is live (reserve/issue from PLANNED), consume/return while in progress or in review; inactive parts/warehouses are refused (read from the DB, not the caller's instance); a warehouse holding stock cannot be deactivated; reserved stock cannot be adjusted away or transferred; quantities: > 0, at most 3 decimals, <= 9,999,999. M06 integration (single contracts, lazy imports): `closure_blockers` gains "parts issued but not consumed or returned" (`part_blockers`); on CLOSE the lines are reconciled, reservations released and never-issued lines cancelled (`on_work_order_closed`); on CANCEL reservations are released and cancellation is refused while issued stock is outstanding (`on_work_order_cancelled`). M07 wraps `request_part` / `consume` (workspace views) and never touches stock. Permissions: `inventory.part.view|part.manage` (organization-wide), site-scoped `inventory.view|warehouse.manage|receive|adjust|transfer|request|reserve|issue|return|consume|reconcile`; role templates (additive): technician +`inventory.consume`, `inventory.part.view`; planner/supervisor +`inventory.part.view`, `inventory.request`; operations manager +`inventory.request|reserve|reconcile`. A technician sees the catalogue and their own part lines but never stock levels or movements. Reorder is information only (low-stock flag when available <= effective minimum); no automatic purchasing. CLARIFICATION REQUIRED (Team Lead): negative adjustments are allowed for stores with `inventory.adjust` (reason required, audited); a two-person approval or a cost/valuation model is not implemented (HPE silent).
- **D-043 M04 Preventive Maintenance design (OUR IMPLEMENTATION DECISIONS; HPE gives scope only: time / meter schedules, recurring job generation, checklists, maintenance windows, reminders; the PM lifecycle SCHEDULED -> DUE -> GENERATED -> ASSIGNED -> COMPLETED -> VERIFIED -> NEXT CYCLE is HPE CONFIRMED).** App `maintenance`. `MaintenancePlan` (asset, site = asset site, priority, estimated hours, optional M08 `checklist_key`, enabled flag) owns `MaintenanceSchedule` rows (TIME: frequency daily / weekly / monthly / quarterly / yearly x interval from a first due date in the SITE's timezone; METER: threshold every N units of an existing M02 `AssetMeter`, counting from `start_value`; lead days, maintenance window = start time + hours in site time, reminder days, `next_sequence` / `next_due_*`, `last_run_at` / `last_error`). Occurrences are numbered: time due(k) = start + k x step (months are added on the calendar from the start date and clamped, so Jan 31 + 1 month = Feb 28 and + 2 = Mar 31: no drift); meter threshold(k) = start_value + k x interval, k >= 1 (HPE example: every 500 h, reading 1200 -> next threshold 1500). Every generated occurrence is a `MaintenanceCycle` (schedule, sequence, due date / value, skipped, work order, trigger scheduler|manual, actor). The PM state of a cycle (GENERATED / ASSIGNED / COMPLETED / VERIFIED / CANCELLED) is DERIVED from the M06 work-order status and never stored twice; schedule state = DISABLED / DUE / SCHEDULED. **Generation goes only through `workorders.services.create_work_order`** (work type PREVENTIVE, plan priority, planned window in the site calendar, then the M06 `plan` transition so the order is PLANNED and waits for assignment); M06 gained `source_type` / `source_id` (migration `workorders.0003`: SERVICE_REQUEST backfilled from `source_request`, PREVENTIVE_MAINTENANCE = the cycle id) with a DB check (type and id together) and a partial UNIQUE index so one PM source has at most one work order. **Duplicate prevention (one cycle = one work order):** the schedule row is locked per generation (concurrent workers serialise), `UNIQUE (schedule, sequence)` and `UNIQUE (source_id) WHERE PM` back it in the database, and the Celery tasks are idempotent (a retry finds nothing due); a failure rolls back cycle, work order and schedule advance together and is recorded in `last_error`. **Missed cycles (CLARIFICATION REQUIRED, Team Lead: HPE and the master workflow only say handle missed / overdue cycles):** implemented as COLLAPSE: when several occurrences are due at once (scheduler outage, meter jump) ONE work order is generated for the latest one, the older ones are counted in `skipped` and named in the order's description, and the schedule continues after it; nothing is replayed. Disabled plan / schedule / suspended organization / retired asset / inactive meter never generate; re-enabling (plan or schedule) or editing the recurrence restarts at the next occurrence that is not in the past (no backlog). Manual Generate now (`maintenance.generate`) creates the NEXT occurrence ahead of its date but is refused while an earlier cycle's work order is still open (a double click cannot create two). The planned window moves to the next working day of the site's default M01 calendar (the due date itself is never shifted). M08: `plan.checklist_key` makes that checklist required for the generated order through `checklists.services.required_templates` (M08 remains the only authority on execution and the completion / closure blockers). Celery: `generate_due_maintenance` every 15 minutes (reminders, then each due schedule in its own transaction, one tenant at a time inside `tenant_context`, suspended organizations skipped) and `generate_schedule` (single schedule, retry on OperationalError). Reminders: one notification per occurrence to users holding `work_order.assign` at the site. Permissions (site-scoped): `maintenance.view|create|update|generate`; the supervisor template gains `maintenance.view` (planner / operations manager already had `maintenance.*`). Not implemented: floating cadence from the completion date, per-schedule assignee defaults, spare-part templates on plans (M09 requirement lines are added by planners per order).

- **D-044 (Phase 6, M11 SLA & Escalation; OUR IMPLEMENTATION DECISIONS, HPE silent on the details; Team Lead confirmation required for business hours and pause states):** HPE CONFIRMED (7.2): response / resolution targets by priority, automated escalation, breach tracking, supervisor alerts. Models `SLAProfile` (organization or site scope, optional work type, `pause_states`), `SLATarget` (per priority: response minutes, resolution minutes, warning %), `EscalationRule` (WARNING / BREACH / ESCALATION after N minutes, level 1-3, recipient role and / or assignee; max 6 per profile), `SLATracking` (one per request or work order, absolute persisted due times), `SLAEvent` (append-only, unique dedupe key), `SLABreach` (unique per tracking and target). Active profile uniqueness per scope (organization / site, work type), a site profile beats the organization one. Editing a profile or target never rewrites running trackings. Permissions: `sla.view` and `sla.acknowledge` (site-scoped), `sla.manage`, `sla.process`; service manager has `sla.*`, operations manager `sla.view` + `sla.acknowledge`. M11 only reads / reacts: M05 / M06 keep their state machines; M14 will consume `/api/v1/sla-metrics/`.
